## Phase 6 (caching: safety guard → reorder → pricing table → breakpoint optimizer)

- [x] Cache pricing sourced live (not guessed) from Anthropic's prompt-caching docs on 2026-07-27: 5m write = 1.25x, 1h write = 2x, read = 0.1x base input price, universal multipliers stacked on each model's own base price — `src/tokenetics/core/cache_pricing.py`
- [x] `CacheSafetyError` — dedicated exception type (not a bare `Exception`), specifically catchable, with a message identifying exactly what changed — `src/tokenetics/core/errors.py`
- [x] Extended `TokeneticsRequest` with `cache_breakpoint: CacheBreakpoint | None` (anchor: `"system"`/`"tools"`, ttl: `"5m"`/`"1h"`); `from_api_kwargs`/`to_api_kwargs` round-trip real `cache_control` block placement, including parsing an already-cached `previous_request` back into a comparable internal shape — `src/tokenetics/core/request.py`
- [x] `CacheReorderGuardStage` (stage 7) — the guard diffs the current request's system+tools against a caller-supplied `config["previous_request"]` (raw API kwargs) and hard-raises `CacheSafetyError` if either changed; the reorder half is a normalize-and-verify no-op given today's already-stable-first request shape (per the 2026-07-27 scoping decision) — `src/tokenetics/stages/cache_reorder_guard.py`
- [x] **Special-cased `CacheSafetyError` in the orchestrator's fail-open framework** — a necessary fix caught while wiring this up: the generic `except Exception:` catch-all would otherwise have silently swallowed the guard's hard-raise exactly like every other stage's failures, defeating the entire point of having one. Added a regression test asserting it actually propagates out of `Tokenetics.prepare()` — `src/tokenetics/orchestrator.py`
- [x] `CacheBreakpointOptimizerStage` (stage 8) — anchors to `tools` if present else `system` (prefix-based caching means one marker at the end of the last stable block caches everything before it too); needs ≥2 matching `config["cache_usage_history"]` entries (`{"timestamp", "content_hash"}`, hashed via `core/cache_hash.py`) to estimate a repeat interval, conservative no-breakpoint otherwise — `src/tokenetics/stages/cache_breakpoint_optimizer.py`
- [x] **Caught and fixed a real modeling bug** while writing this stage's tests: the first version compared each TTL tier's *total* expected benefit independently over its own window, which meant the 1-hour tier's larger window always won mathematically (more window = more assumed reads), so the 5-minute tier could never actually be selected even at very short repeat gaps. Fixed by recognizing that a cache read refreshes its own TTL — once a tier's window covers the repeat gap, the cache stays continuously warm off one amortized write, so the cheapest viable tier should win. Redesigned to a simple "cheapest tier that stays warm" rule; the pricing multipliers are now used for an informational net-benefit estimate logged alongside the decision, not for the tier choice itself.
- [x] **Caught and fixed a second real gap, post-Phase-6, via `--measure-usage` against the real API (2026-08-02)**: `cache_hit`'s real `usage.cache_creation_input_tokens`/`cache_read_input_tokens` both came back 0 despite the stage logging `breakpoint_placed=True` — first traced to a per-model minimum cacheable prefix length (1024 tokens for `claude-sonnet-5`) that the real API enforces silently, with no error, just an ordinary uncached request. Added `MIN_CACHEABLE_TOKENS` (sourced live, same doc, re-verified 2026-08-02) to `core/cache_pricing.py`, and the stage declined to place a breakpoint below that minimum (`reason="prefix_below_minimum_cacheable_size"`). `cache_hit`'s demo system prompt and `cache_benchmark.py`'s three traffic profiles were resized above the threshold.
- [x] **Caught and fixed a third, more fundamental gap in the same investigation**: even after the resize, the numbers still came back 0/0. Root cause was the anchor-selection logic itself: Anthropic's cache hierarchy is `tools -> system -> messages`, and a breakpoint caches everything up to AND INCLUDING the block it's on, in that order — so a marker on the last `tool` caches **only the tools array**, never the `system` prompt after it. The stage had been anchoring to `"tools"` whenever tools were present, on the mistaken assumption (confirmed live against the docs, 2026-08-02) that this also covered `system` — it was confusing the JSON *key* order `to_api_kwargs` happens to emit (system, tools, messages) with Anthropic's actual cache-*hierarchy* order (tools, system, messages), which is the reverse for system/tools. For `cache_hit`, this meant only the ~30-token tools array was ever being offered to the cache, far below the minimum, regardless of how large the system prompt was. Fixed by anchoring to `"system"` whenever one exists (covers tools+system together) and only falling back to `"tools"` when there's no system to fold in — `src/tokenetics/stages/cache_breakpoint_optimizer.py`. `cache_reorder_guard.py`'s docstring (the likely source of the original confusion) was also corrected. **Confirmed end-to-end against the real API same day**: `--all-scenarios --measure-usage` showed `cache_hit`'s pipeline-enabled call writing a real `cache_creation_input_tokens=1724`, then an immediate repeat call reading those same 1,724 tokens back via `cache_read_input_tokens` — the full write-then-read cycle, measured, not just unit-tested.
- [x] Synthetic-traffic benchmark, per this phase's explicit build-order requirement (distinct from Phase 9's real-corpus benchmark suite) — `scripts/cache_benchmark.py`, no network calls, deterministic. Headline numbers at 1000/5000 simulated calls across three traffic profiles (hot/warm/cold, each sized above the real per-model minimum cacheable prefix — see the `cache_breakpoint_optimizer` minimum-size fix below): **~28-31% cheaper than never caching, ~10-11% cheaper than a naive always-5m-breakpoint habit**, ~80% cache hit rate
- [x] Repositioned in the fixed pipeline order: `... → context_scheduler → cache_reorder_guard → cache_breakpoint_optimizer → structured_output → ...`
- [x] Tests, including the standalone hard-raise test required before anything else in this phase per CLAUDE.md — `tests/test_cache_reorder_guard.py`, `tests/test_cache_breakpoint_optimizer.py`, `tests/test_cache_pricing.py`, `tests/test_cache_hash.py`, plus cache-control round-trip tests added to `tests/test_request.py`
- [x] `scripts/dev_demo.py`: `cache_hit` scenario (breakpoint optimizer placing a 5m breakpoint) and `cache_guard_violation` scenario (demonstrates the hard-raise, caught and printed rather than crashing `--all-scenarios`)

**Known stub-only artifact, not a real bug**: `dev_demo.py`'s offline (`StubAnthropicClient`) token counts show `cache_breakpoint_optimizer` "costing" tokens when it places a breakpoint — this is the stub's `len(str(system))` approximation reacting to `system` becoming a block-list once `cache_control` is attached, not a real cost. The real Anthropic API only counts actual text content, not JSON/cache_control structure; against the real API this stage should show ~0 request-token change.

## Phase 7 (structured delta compression + `apply_delta()`)

- [x] **Join-key design (resolved 2026-08-02)**: scoped to `tool_result` content blocks only, keyed by `tool_use_id` — `config["previous_payloads"]: dict[str, str]` maps a tool_result's `tool_use_id` (unique within the current request, already known to the caller when constructing that reply) to whatever they consider its previous version. General prose-text repeats stay near_dup's job. See the brief's stage 6 amendment for the full resolution.
- [x] `src/tokenetics/core/delta.py` — `compute_delta`/`apply_delta`, stdlib-only (`difflib` + `json`, no new core dependency). Two content shapes, auto-detected: JSON content (both previous/new parse as an object/array) gets a minimal hand-rolled structural patch (add/remove/replace by escaped JSON-pointer-style path, RFC 6902-flavored subset, not the full spec); everything else gets a line-level patch via `difflib.SequenceMatcher` opcodes, applied by directly replaying those opcodes against `previous` rather than re-parsing unified-diff hunk text (avoids real correctness risk for no benefit, since nothing outside the module ever reads a human-authored diff). `DELTA_SIZE_RATIO_THRESHOLD = 0.6` — a plain documented constant (not pricing/compat data, so no versioned table, same precedent as near_dup's similarity thresholds).
- [x] **"Exact" round-trip means two different things by design**: line-patch reconstruction is byte-exact; JSON-patch reconstruction is semantically exact (`json.loads(apply_delta(...)) == json.loads(new)`, re-serialized via `json.dumps(..., sort_keys=True)`) — tool-result payloads are data, not formatted prose, so byte-exact JSON formatting was never a real invariant worth preserving. Documented explicitly in the module docstring so it reads as a decision, not an oversight.
- [x] `DeltaCompressionStage` (stage 6) — `src/tokenetics/stages/delta_compression.py`. Only `tool_result` blocks whose `content` is a plain string are eligible (list-of-blocks content, e.g. an image result, is left untouched — conservative by default, not guessed at); falls back to full content when the encoded delta isn't meaningfully smaller than the threshold.
- [x] Repositioned in the fixed pipeline order: `... → context_scheduler → delta_compression → cache_reorder_guard → ...`
- [x] Tests: `tests/test_delta.py` (round-trip correctness for both shapes, no-change case, totally-different-content-returns-None, path-escaping, JSON top-level-type-change fallback, marker-rejection) and `tests/test_delta_compression.py` (stage-level matching/skipping behavior, multi-block requests, plus the deliberately-broken-plugin fail-open regression test required before any stage is considered done — a malformed content block crashes the stage internally, and the orchestrator must catch it and pass the request through unmodified). Pipeline-order assertion updated in `tests/test_orchestrator.py`.
- [x] `scripts/dev_demo.py`: `delta_hit` scenario — a tool_result whose JSON content differs from a caller-supplied previous version by one field out of many; offline-verified 1035 → 113 chars (single-op JSON patch), confirmed it survives the full pipeline unmodified through every later stage.
- [x] **Deliberately deferred, not resolved here**: whether Claude actually interprets a delta-encoded tool_result correctly (vs. just seeing the full payload) is a real model-quality question, not a mechanical one — belongs in Phase 9's held-out quality-check set, same treatment as brevity/thinking-effort tuning, not assumed to just work. Flagged in both the brief and the stage's own docstring.

## Phase 8 (Tier 0 assembled in fixed order, end-to-end integration, frozen API)

This phase wasn't "build the pipeline" — all 10 request-side stages plus `PostHocTrimStage` were already wired into the orchestrator in the correct fixed order incrementally as each earlier phase landed. It's "prove the whole pipeline holds together and lock its public surface":

- [x] **End-to-end integration test** — `tests/test_tier0_integration.py::test_end_to_end_pipeline_runs_in_the_documented_fixed_order` runs a realistic multi-turn, tool-using conversation through the *entire* pipeline and asserts the logger's runtime stage trace matches CLAUDE.md's fixed order exactly — not just the static stage list (already covered by `test_orchestrator.py`), the actual execution order over a real request. A companion test confirms the output is well-formed enough for the real API: alternating roles, first message `user`, the relevant tool survived.
- [x] **Stage 4/5 double-prune regression test** — `test_stage_4_and_5_never_double_prune_the_same_content`. Schema minification (stage 4) only ever prunes `request.tools`; the context scheduler (stage 5) only ever prunes `request.messages` — disjoint fields by construction (confirmed by reading both stages' source, each returns `replace(request, tools=...)` / `replace(request, messages=...)` respectively, never the other). The test proves this holds under a real *combined* run, not just code inspection: a request with both an irrelevant tool and a tight token budget in play at once, asserting each stage's log only ever mentions its own kind of drop (`dropped_tools` vs. `dropped_turns`), never the other's.
- [x] **Contract/signature test on `Tokenetics.prepare()`/`finalize()`/`__init__`** — `test_prepare_signature_is_frozen`, `test_finalize_signature_is_frozen`, `test_tokenetics_init_signature_is_frozen`, via `inspect.signature`. A later phase changing these signatures now fails a test instead of silently drifting.
- [x] **Tier 0 API frozen** as of 2026-08-02. Per CLAUDE.md's "don't jump ahead" rule, Phase 9 (benchmarking) and everything after it should not have started before this milestone — it now has.
- [x] **A real crash in `finalize()` caught much later (2026-08-12), during a live Phase 11 dashboard hand-check, fixed same day**: a response whose visible text ended in a trailing newline crashed `Tokenetics.finalize()` with a 400 from the real API — `count_text_tokens()`'s own `count_tokens` call wraps the extracted text as a synthetic assistant message to measure it, and the Messages API rejects any assistant content ending in trailing whitespace, `invalid_request_error: final assistant content cannot end with trailing whitespace`. Not just a counting-endpoint quirk: `finalize()`'s own stated contract is "text ready to store/re-inject as future context" — text with trailing whitespace was never actually valid for that; re-injecting it as history on a later turn would have hit the identical 400 from a real completion call. Fixed by stripping trailing whitespace from the extracted text immediately, before any response-stage processing (including the token count that crashed) — `text = "".join(...).rstrip()` in `orchestrator.py`'s `finalize()`. This slightly changes `finalize()`'s behavior with an empty `response_stages` list (previously a strict no-op on the extracted text; now still strips trailing whitespace, since that's a real API validity requirement, not a stage's job) — `tests/test_finalize.py` updated to describe this precisely, plus a new regression test reproducing the exact crash case. This is a Tier 0 core fix (`orchestrator.py`, frozen-API territory, though only `finalize()`'s *signature* is frozen, not its internals) surfacing well after the freeze — flagged here rather than silently folded into a later phase's notes, since it affects every phase's response-side text, not just the phase where it was found.

## Phase 9 (benchmark suite — real measured numbers)

A different flavor from 0–8: not new pipeline stages, but running the now-frozen Tier 0 pipeline against real data and reporting honestly on what it does. First phase with sustained real spend, not just occasional dev_demo spot-checks.

- [x] **Quality-grading methodology (resolved 2026-08-02)**: a hand-written rubric's `required_elements` (facts/keywords that must appear in the response) is the authoritative, objective pass/fail gate for the held-out quality-check set. An optional LLM-judge score is a secondary signal only — grading Claude's output by asking Claude is reasonable as a cheap secondary check, but using it as sole authority in exactly the risk-bearing cases this set exists to catch would undercut the whole point.

## Phase 10 (Tier 2 extras)

Three independent, opt-in plugins layered on the frozen, benchmarked Tier 0 core — per the brief, there's no fixed *ordering* requirement between them the way Tier 0's 11 stages have (CLAUDE.md's pipeline-order lock is a Tier 0 constraint), but they still need to be built one at a time. Build order below is a sequencing choice, not a brief requirement — starting with the smallest, dependency-free one first to validate the whole "opt-in extra" pattern (new `pyproject.toml` extras group, fail-open on unavailability, its own benchmark separate from Phase 9's suite) before taking on the two that need heavy new dependencies.

**Non-negotiables carried over from CLAUDE.md, apply to all three:**
- Tier 2 dependencies (`torch`, `transformers`, embedding models, vector stores) live behind their own extras group — never a base-install dependency, never imported at module load time outside that extra's own code path.
- Each is fail-open to plain Tier 0 behavior (or a normal, uncompressed/uncached API call) if its dependency isn't installed or its runtime fails — same fail-open discipline as every Tier 0 stage, not a lighter bar just because it's optional.
- Each ships its *own* benchmark, separate from Phase 9's corpus/quality-check suite (which stays Tier-0-only) — Phase 9's suite is not extended to cover these; a new, extra-specific measurement each time.
- Tested only under their own extras install (`pip install tokenetics[compress]` etc.) — never pulled into the core `pytest` run, so a base install's CI never needs `torch`.

- [x] **Mechanism, word-granularity, not raw sub-token dropping**: each token is scored by its own negative log-likelihood given prior context (high loss = surprising = informative = keep; low loss = predictable = redundant = safe to drop) via one real forward pass through the causal LM. ### Third pass (2026-08-12): fixed a real negative-savings bug caught via a live dashboard run

User ran the handed-back commands for real, got a genuinely confusing result: `-8.0%` overall "savings" with clean data (no crashed-run contamination — `post_hoc_trim`'s run count matched every other stage's, ruling out the artifact from the previous round). Root cause, diagnosed from the actual numbers rather than guessed: `post_hoc_trim` is the one response-side stage — it measures the **reply's** token count via `count_text_tokens`, a completely different axis from every other (request-side) stage, which measures the **request's** token count via `count_tokens`. `aggregate()`'s per-run "overall savings" picked "first stage's `tokens_before` -> last stage's `tokens_after`" without distinguishing the two — and since `post_hoc_trim` runs last (in `finalize()`, after `prepare()`'s 11 request-side stages), any run that called both ended up comparing **request size before optimization** against **reply length**, not request-before vs. request-after. Real replies are routinely longer in tokens than an optimized request, which is exactly why this trended negative — it was never measuring real token reduction at all.

- [x] **`orchestrator.py`**: `_run_stage`'s two `log_stage()` calls now tag `phase="request"`; `_run_response_stage`'s two calls tag `phase="response"`. **Decision (discussed with the user, not unilateral)**: two options were on the table — lower the effort levels (e.g. `"high"` → `"medium"`), or stop auto-setting thinking effort entirely and require an explicit opt-in. Chose **opt-in**, for two reasons: (1) lowering the level is a guess that would need its own real-money re-test to validate, with no guarantee `"medium"` isn't *also* net-negative; (2) opt-in is the *consistent* choice, not a bigger departure — every other cost/benefit tradeoff in this project already defaults safe with explicit opt-in for aggressive behavior (`tale.py` is entirely opt-in; `compress`'s `RECOMMENDED_MAX_RATIO` clamps by default, needs `allow_above_recommended_max=True` to exceed). ### Post-fix re-run (2026-09-04) — same result, revealing a second, more precise root cause

Re-ran `usage --confirm-spend` after shipping the opt-in fix. **Result: essentially unchanged (-25.5% overall, `code`/`conversational` losses nearly identical sample-for-sample to the pre-fix run)** — several samples matched to within 0.1 percentage points (`code_001`: -136.0% both times, `code_014`: -136.1% both times, `code_017`: -137.1% both times). That level of reproducibility across separately-run real completions is itself a clue: it doesn't look like content variance, it looks like something hitting the exact same ceiling both times.

**Verified directly, not guessed, before writing any more code**: offline-checked `code_001` and confirmed `thinking_effort_skipped: 'opt_in_not_enabled'` and `thinking: None` in the prepared request — the fix was working correctly. Yet the cost pattern persisted. So thinking effort was never the (sole) cause; the earlier diagnosis had picked the wrong variable. A small, cheap, targeted diagnostic (5 samples, ~$0.05, `stop_reason` captured on every call) confirmed the real cause: **every single completion in both conditions — baseline AND pipeline — showed `stop_reason="max_tokens"`.** Every one was truncated. `code_001`/`code_014` baseline cut off at 400 tokens, pipeline cut off at 960 (still truncated, just later); `code_005`/`code_007` (the ones showing exactly +0.0%) turned out to never get widened at all (`prepared max_tokens=400`, unchanged from the caller's own value — very likely a task-classifier mismatch, the same pattern already seen once before with `tool_heavy_017`).

**The actual root cause**: `benchmarks/corpus/`'s `max_tokens` values (400 for `code`, 300 for `conversational`) were deliberately set tiny for Phase 9's own purpose — proving `adaptive_budget`'s widening mechanism correctly fires under a tight cap — not to represent what a realistic caller would set. Reusing that corpus unmodified for a *dollar-cost* benchmark meant every comparison was "truncated garbage at 400 tokens" vs. "still-truncated-but-less-garbage at 960 tokens" — neither a complete, useful answer, and the wider one costs more purely because it wrote more before also getting cut off. Not a fair test of real efficiency.

- [x] **Fixed in `benchmark_runner.py`, not by touching the corpus**: `_REALISTIC_MAX_TOKENS_FLOOR = 2048` (chosen from real observed reply lengths in this project's own `dev_demo.py` runs — thorough code/explanation answers commonly ran 700-960 output tokens — generous headroom, not a guess) applied via `_with_realistic_max_tokens()` to BOTH the baseline and pipeline calls identically, in both the cost estimator and the real run. The corpus itself is untouched — Phase 9's widening-correctness tests still need the original tight caps and still have them.
- [x] With the floor in place, `adaptive_budget`'s own widening will often no-op (the caller's cap already exceeds its heuristic) — correct, and it isolates whether the OTHER mechanisms (dedup, near_dup, schema_minification, context_scheduler, delta_compression, caching) save money once truncation stops confounding the result.
- [x] Dry-run cost re-estimated: **$1.75** for the full 83-sample corpus at the new floor (up from $0.31 — expected, since allowing genuinely longer, complete replies costs more than truncated ones, by design). It answers "does this help on someone's first-ever message," not "does this help across a real session" — those are different questions with different honest answers.

## Real multi-turn session benchmark (`benchmark_runner.py session`) — built 2026-09-05

Built because the honest answer to "why no net savings" pointed straight at `usage`'s own structural blind spot: it can't see caching amortize past a single write, and it can't see redundancy accumulate the way a real conversation does. `session` tests that directly, with real completions.

- [x] **`benchmarks/session/realistic_session.json`**: one realistic 8-turn conversation (code question → real bug fix → near-duplicate padding → a genuine decision → more padding → a tangent → an extraction request → a final recap that requires remembering the earlier decision), with the SAME system prompt reused across every turn (so caching gets a real chance to amortize past the first write, unlike a one-shot corpus sample) and genuine accumulated redundancy for `dedup`/`near_dup`/`context_scheduler` to actually prune. `max_tokens=800` (realistic, well above what these turns naturally need — the truncation lesson from `usage` applied here from the start, not re-discovered the hard way again).
- [x] **Two parallel real threads, run turn by turn**: `baseline` (raw request/reply every turn, no Tokenetics, never cached — what a caller who never adopted Tokenetics would actually pay) and `pipeline` (`prepare()`/`finalize()` every turn, with a real, incrementally-grown `cache_usage_history` fed forward exactly as a real caller tracking their own repeat pattern would build it). The two threads' histories diverge in content turn to turn (separate real completions) — expected and correct, since this measures "what would my bill look like across this session if I'd used Tokenetics from turn one," not a replay of identical content.
- [x] **A real bug caught and fixed before spending money, via an offline structural dry-run (stub client, fake replies, zero cost)**: the session originally registered one never-used tool (to also exercise `schema_minification`), but `schema_minification` runs earlier in the fixed pipeline than `cache_breakpoint_optimizer` — and one turn's text ("what's a good weekend activity if the **weather's** nice") coincidentally lexically matched the tool's name, making it unpredictably survive on that one turn only. That changed the actual stable prefix the cache stage sees turn to turn, breaking the repeat-pattern match against this benchmark's own precomputed hash — confirmed directly (`cache_breakpoint_optimizer` fired on only 1 of 8 turns) before it ever became a real-money mistake. Fixed by removing the tool entirely (schema_minification is already covered elsewhere; it's not this benchmark's concern, and having it silently perturb the cache prefix defeated the point). Re-verified offline: the cache breakpoint now fires consistently from turn 3 onward (turns 1-2 correctly show `insufficient_usage_history` — not enough evidence yet, conservative and correct), `near_dup` catches the duplicate padding from turn 5, `context_scheduler` starts pruning once there's real accumulated content.
- [x] Same cost-ceiling gating as `usage`/`quality-check` (`--dry-run`/`--confirm-spend`/`--cost-ceiling`). Dry-run: **$0.1556** for 8 turns × 2 threads (16 completions).
- [x] Ruff/mypy clean; 299-test suite unaffected (script + data only, no source module touched).

- [x] **Real run happened (2026-09-05): net +16.0% cheaper** ($0.052282 → $0.043923) — the first genuinely positive, substantial verdict in this whole benchmarking arc. Turn-by-turn: turns 1-2 slightly more expensive (no cache activity yet, still building evidence), turn 3 a real cache **write** (-14.8%, the one-time premium), turns 4/5/6 real cache **reads** off that write (+38.9%/+42.1%/+29.3%), turn 7 a **second** write (-14.6% — the turn-3 write had expired), turn 8 a read off the fresh write (+38.2%). A clean, textbook demonstration of the write-then-amortize pattern `cache_breakpoint_optimizer` is built around, confirmed with real money.
- [x] **The turn-7 re-write led directly to a real bug fix, not just an observation**: `cache_breakpoint_optimizer`'s `_choose_ttl` picked the 5m tier based on the *average* observed repeat gap, with no safety margin — a few fast early gaps (turns 1→2→3) pulled the average comfortably under 5 minutes, but real generation/network latency between turns 3 and 7 pushed that specific gap past the window, expiring the cache and forcing an unplanned second write. Root cause: averaging hides exactly the gap that will recur and cost money; nothing in the decision asked "what's the worst gap we've actually seen," only "what's typical."
- [x] **Fixed same day**: `_choose_ttl` now decides based on the **maximum** observed gap, not the average — if any past gap already exceeded a tier's window, that tier is no longer eligible, even if other gaps were fast. Trades a bit more upfront write cost (1h's 2x premium vs. 5m's 1.25x) for avoiding a strictly worse outcome (a surprise re-write that also forfeits whatever reads the shorter tier might have delivered) — matching this project's conservative-by-default principle used everywhere else (`adaptive_budget` widens rather than narrows, `schema_minification` keeps ambiguous tools). The informational net-benefit estimate logged alongside the decision still uses the average (a genuine "how much do we expect to save" question, not a safety margin) — only the tier-selection safety check changed.
- [x] New regression test (`test_a_few_fast_gaps_then_one_slow_gap_does_not_pick_the_5m_tier`) reproduces the exact gap shape from the real session (60s, 60s, 60s, 400s -- average 145s looks safely under the 5m window, but the 400s max isn't) and confirms it now correctly lands on the 1h tier instead. All 9 pre-existing tests passed unchanged (every one of them used uniform gap spacing, where average and maximum are numerically identical, so this fix was invisible to them — exactly the kind of case that needed a dedicated non-uniform test to catch at all). 300 tests total, ruff/mypy clean.

**Net result of the whole investigation, start to finish**: isolated one-shot requests are roughly cost-neutral (`usage`, -2.1%, within normal variance); a real, repeated-traffic multi-turn session is genuinely and substantially cheaper (`session`, +16.0%), and the one real inefficiency that session run surfaced (a cache tier picked without a safety margin) is now fixed and regression-tested. This is the complete, honest, evidence-based answer to "what does Tokenetics actually save" — not a single flat percentage, exactly as CLAUDE.md's benchmarking discipline requires.
